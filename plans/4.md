# Plan for #4: Filter runs by vehicle on the web page

## Goal
Users can type a vehicle ID above the runs table and immediately see only matching rows. Existing API behavior, run creation, and seeded data stay unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- confirmed, change: yes - `public/index.html`: renders the runs table and fetches `/api/runs`; add a labelled `Filter by vehicle` input and client-side row filtering.
- confirmed, change: yes - `e2e/smoke.spec.ts`: existing browser coverage for `/`, table rows, and adding a run; add coverage that typing `WVW-1001` leaves only that vehicle's runs visible and clearing restores all rows.
- confirmed, change: no - `src/runs.ts` `SEED_RUNS`: includes two `WVW-1001` runs and other vehicles, which gives the Playwright test deterministic filter data.
- confirmed, change: no - `src/app.ts` `GET /api/runs`: API already supports optional `vehicleId`; this ticket allows client-side filtering, so no route change is needed.
- confirmed, change: no - `test/app.test.ts`: API filtering is already unit-tested; no unit-test change expected for UI-only behavior.
- confirmed, change: no - `src/config.ts`, `k8s/configmap.yaml`, `README.md` environment table: no new environment variable is required.

## Tests
- Add/update `e2e/smoke.spec.ts` with a Playwright test that locates the `Filter by vehicle` input by label, fills `WVW-1001`, asserts only `WVW-1001` rows are visible, then clears it and asserts all seeded rows return.
- Keep the existing browser test passing.

## Environment contract
No environment variable changes. `src/config.ts`, `k8s/configmap.yaml`, and the README environment table stay in sync without edits.

## Risks
- Browser: filtering could hide newly created rows incorrectly or leave stale rows after clearing.
- Browser: accessible label/role selectors could fail if the input is not labelled properly.
- Pipeline: `test` can fail on TypeScript/build regressions; `deploy-kind` browser step can fail if the page filter breaks in the deployed app.
- Rollout/stability/smoke risk is low because no server, config, manifest, or health route change is planned.

## Open questions
None.

## Decisions
- Use client-side filtering because the issue explicitly allows it and avoids unnecessary API changes.
