# Plan for #5: Enable the metrics endpoint in the deployment

## Goal
This change makes the deployed app expose a second metrics port, so ops can scrape runtime metrics. The app already supports a plain-text listener when `METRICS_ENABLED=true`; the deployment currently disables it.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- confirmed: `src/config.ts` — `loadConfig` reads `METRICS_ENABLED` and requires `METRICS_PORT` when enabled; this is the source of startup validation. change: yes
- confirmed: `k8s/configmap.yaml` — deployment env values are set here, and `METRICS_ENABLED` is currently `false`. change: yes
- confirmed: `k8s/deployment.yaml` — container ports define the HTTP port and will need a second `metrics` port to expose the listener. change: yes
- confirmed: `k8s/service.yaml` — service ports map the pod ports and must expose the metrics service if required by deployment convention. change: maybe
- confirmed: `src/server.ts` — metrics listener is started only when `config.metricsEnabled && config.metricsPort`; the app already emits metrics text. change: no
- confirmed: `README.md` — environment contract and operations docs include the metrics variable table and deployment flow; it must document the metrics endpoint. change: yes
- plausible: `public/index.html` or `e2e/` — browser or UI pages may not need changes because this is deployment-only and metrics are not user-visible. change: no
- open: whether the metrics endpoint should be exposed via the main Service or only as pod port/service port; the ticket says “deployed pod exposes metrics on a second container port named `metrics`,” which suggests pod exposure only. no code change yet

## Tests
- `test/app.test.ts` — verify `METRICS_PORT` validation and config behavior continue to match the env contract.
- pipeline deploy smoke — confirm rollout and smoke succeed after enabling metrics in the deployment.
- browser or smoke check — ensures the app still responds on `/health` when the metrics port is enabled.

## Environment contract
- No new environment variables are required; this change uses the existing `METRICS_ENABLED` and `METRICS_PORT` contract in `src/config.ts`.
- `k8s/configmap.yaml` and `README.md` are in scope because the deployment must set `METRICS_ENABLED=true` and `METRICS_PORT=9100` (or another valid port) in the same change.

## Risks
- If `METRICS_PORT` is not set or is equal to `PORT`, the app exits at startup; pipeline rollout fails with a crash loop.
- A deployment with a second port but no service or selector mismatch could still pass app startup yet fail the smoke/rollout checks.
- The browser and smoke checks might fail if the readiness path or container port names are misconfigured.

## Open questions
1. Should the service expose the metrics port as a named port on the same Service, or only the pod container port is required?
2. Is `9100` the expected port for the deployed metrics listener, or should we use a different non-conflicting port in the manifest?

## Decisions
- The pod will expose metrics on a second container port named `metrics`; the Service does not need to publish a second port.
- The deployment will use `METRICS_PORT=9100` to match the app's config contract and avoid conflicts with the HTTP port on `3000`.
